    About Saturn Devouring

    Saturn Devouring is a free, fan-made horror game with MIT-licensed original code inspired by the Halo universe. It is set aboard the UNSC Saturn Devouring, a Charon-class frigate orbiting Mars during the events of Halo 3. Rendered dead in space by High Charity’s slipspace rupture to the Ark, the crew must investigate a small impact to the ship caused by the same event.

    Saturn Devouring is randomly generated; no two playthroughs are identical. Each game features a different combination of crash site, broken doors, broken lights, and disrupted radio comms as you fight to contain the Flood infection. The Flood acts as one real hive mind. It starts small in number, but quickly begins consuming bodies and producing more infection forms. If you let it. A small initial infection quickly turns to infestation, unless you can snuff it out first.

    Saturn Devouring is a web-native game, meaning you can play it on any device with a capable browser and a keyboard or controller. Play solo or, recommended, with a friend via co-op. WebRTC connects your fireteam directly, whether you are playing over the same router or across the internet.

    Architecture overview

    Saturn Devouring separates the deterministic ship simulation from rendering and player input. The simulation writes one packed agent buffer; the 3D layer consumes it without owning world state.

    PRIMARY SURFACES

    • sim/ — ship graph, factions, combat, commands, and deterministic ticks.
    • game/ — first-person controls, 3D world, HUD, audio, and the hub launcher.
    • multiplayer/ — room abstraction, lobby protocol, game synchronization, and voice.

    Co-op protocol

    The peerd build calls the consent-gated dwapp bridge. The web build bundles peerd’s identity, room, mesh, gossip, presence, direct-message, and WebRTC transport primitives.

    FLOW

    • Join a room and authenticate peers with did:key identities.
    • Quick Match discovers the fullest open public lobby and creates one only if none answers; private lobby messages require a DID-bound invite HMAC.
    • A nonce-bound join remains rollback-safe until the requester acknowledges exact commit delivery, so a delayed commit cannot leave a ghost member after timeout.
    • The lobby creator may deploy after a second player joins, or keep waiting up to four. Optional capacity ranking chooses simulation authority separately; otherwise DID order is deterministic.
    • A proposal/ack/commit-receipt/go-receipt/final-launch barrier freezes membership before deployment.
    • The fireteam leaves the lobby for an isolated match room.
    • The authority advances the ship simulation and sends term-bound delta checkpoints; player poses and validated actions use direct WebRTC messages.
    • The standalone adapter offers native RTP/Opus voice; the current Peerd bridge hides voice because it does not expose media operations.
    discover → join / accept / admission-ack → ready → proposal / receipts → final launch → match room
                                              ↘ direct state and actions

    peerd dwapp package

    The hub output contains a schema-1 peerd.json declaring kind: "dwapp", one entry HTML document, one stylesheet, and one self-contained readable module bundle. Textures and audio remain byte-identical binary files resolved through peerd.assets in the opaque-origin sandbox.

    BRIDGE OPERATIONS USED

    The current bridge provides hello, join, leave, presence, announce, subscribe, publish, retain, history, and dm-send. Optional capacity and voice operations are used only when advertised by a future bridge.

    npm run build:dwapp
# output: dist/dwapp/hub/

    Run and verify

    Use any static server for the web build. Co-op requires a secure browser context outside localhost because microphone capture and WebCrypto are secure-context APIs.

    npm run serve
npm run multiplayer
npm run determinism
npm run build:dwapp
